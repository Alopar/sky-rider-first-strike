# UI на SVG и экранный слой

Одна из ключевых гипотез проекта: **весь** UI — не только иконки, а и окна, подложки, кнопки, бары — собирается из SVG. При этом UI **не рисуется внутри игрового Phaser-canvas**: он живёт в **screen view / UI view** — отдельном слое (viewport) **того же размера**, что и canvas со сценой. Игровой canvas (**world view / game view**) оставляем для мира: фон, юниты, снаряды, эффекты. В canvas допустимы только игровые элементы (например всплывающие числа урона в координатах мира); счётчики, панели, модалки и меню — только в UI-слое.

Документ описывает роль UI, откуда берётся графика и как это согласуется с Phaser.

## Зачем

- Единый визуальный язык с игровой графикой (та же семантика SVG).
- Бесшовное масштабирование под разные разрешения без артефактов.
- Состояния (hover, pressed, disabled, focused) можно выражать сменой классов, вариантов SVG или параметров пайплайна — на усмотрение UI Toolkit.
- Темизация: смена палитры или набора ассетов без переписывания игровой сцены.
- Редакторский цикл: дизайнер открывает `.svg` в `assets/`, правит формы и детали, коммитит файлы — без поиска строк внутри JS.

## Где лежат SVG

**Исходники UI-графики — только в ассетах**, например ветка каталога вроде `assets/svg/ui/` (точная раскладка — по мере появления кода). Файлы:

- можно открыть в векторном редакторе и в браузере;
- версионируются как обычные ресурсы;
- не дублируются как зашитые в JS многострочные строки.

Как именно ассет попадает на экран — решает **UI Toolkit**: вставка в DOM (`<img>`, `inline`, спрайт-лист), предзагрузка и кэш, запекание в растровую текстуру для отдельного UI-canvas (если такой выберем) и т. п. Допустимо при старте игры подтянуть SVG, закэшировать результат или один раз преобразовать в формат, удобный для рендера — без жёсткой привязки документа к одной технологии.

## Где живёт код

Логика разметки, состояний и привязки к событиям — в `src/ui/` (или согласованном модуле). Там же фасад вида «собери кнопку / окно / панель из ассета X с параметрами Y». Структура папок уточняется при реализации; ориентир:

```
src/ui/
  (фасад: кнопки, окна, панели, бары — из путей к assets/svg/ui/...)
  (компоненты: обработка pointer/keyboard, состояния, подписка на EventBus)
```

Шаблоны SVG **не** храним как «одна большая строка в `button.js`» — вместо этого путь к файлу и параметры наложения (палитра, масштаб), если toolkit это поддерживает.

## Как согласовать слой с Phaser

1. В разметке страницы игровой **Phaser canvas** и **UI-viewport** (контейнер) совмещают по размеру и позиции (например общая обёртка и абсолютное позиционирование слоя UI поверх canvas).
2. UI-viewport получает корректные `pointer-events`, чтобы клики по кнопкам доходили до UI, а «пустые» области по политике проекта либо пробрасывают события к игре, либо блокируют — это фиксируем в UI Toolkit.
3. Игровой ввод (стрельба, движение корабля) обрабатывается в зоне world view; HUD и меню читают и пишут состояние через те же каналы, что и раньше (например `EventBus`), но визуально рисуются только в UI-слое.

## Состояния кнопки

Семантика состояний прежняя:

- `idle`, `hover`, `pressed`, `disabled`, `focused` (для клавиатурной навигации по меню).

Реализация: отдельные SVG-файлы на состояние, или один файл с переключаемыми слоями/классами, или растеризация в текстуры — **на усмотрение UI Toolkit**. Подписи на кнопках могут быть частью SVG или отдельным текстовым слоём в UI-viewport для кросс-браузерности со шрифтами.

## Окна и модалки

Окно — подложка из ассета (тень, обводка, градиент), зона заголовка, контентная зона для вложенных контролов, опционально кнопка закрытия. При изменении размеров — пересчёт layout в UI-слое или отдельные ассеты для типовых размеров; 9-slice на усмотрение toolkit.

## HUD

Весь HUD (здоровье, счёт, уровень оружия, иконки, бар босса) — **в UI-viewport**, не как список `Image` внутри игрового canvas. Подписка на `EventBus` (например `player:hp-changed`, `score:changed`, `weapon:level-changed`, `boss:spawned`, `boss:hp-changed`) остаётся каноническим способом синхронизации данных с экраном.

## Меню и стартовый экран

Экраны главного меню, выбора уровня, паузы, game over и победы — целиком в **screen view**. Иерархия «сцен» может быть выражена роутингом по DOM, стеком видов в UI-модуле или отдельным мини-фреймворком; Phaser-сцены при этом отвечают за **мир** (загрузка уровня, геймплей), а не за отрисовку панелей поверх мира в том же canvas.

Навигация мышью и с клавиатуры; для клавиатуры обязательна визуализация `focused`.

## Производительность

- **Много уникальных комбинаций** — кэш на уровне toolkit (один и тот же ассет + параметры не дублируют тяжёлый рендер).
- **Пересборка во время боя** — не создавать заново тяжёлые ресурсы в горячем цикле геймплея; предзагрузка в фазе загрузки игры.
- **Крупные SVG** — упрощать декор окна; тяжёлые фильтры по возможности избегать.
- **Ретина** — если запекаем в bitmap, учитывать `devicePixelRatio` в пайплайне toolkit.

## Тестирование UI без игры

В отладочной сборке — отдельная страница или режим «витрина компонентов», который поднимает только UI-viewport и моки событий, без запуска полноценного `GameScene`. Это ускоряет итерации по визуалу.

## Враги и UI

Враги визуально тоже строятся из **SVG в `assets/`** (например `assets/svg/enemies/`), см. `architecture.md` и `visual-style.md`. Общий принцип один: исходник векторный лежит в ассетах; отличие лишь в том, что Game Toolkit забирает их в мир Phaser (текстуры, спрайты), а UI Toolkit — в экранный слой.
